01Agent Loop 设计

electron/core/agent/harness.ts · Harness.run() / finishRun()

Harness 的循环就是一个 for(;;)：每一轮准备上下文、调一次模型，如果模型返回了工具调用，就执行这些工具，把结果写回历史，再进入下一轮。模型不再调用工具时，要先通过一组完成门禁才算结束。它和普通 ReAct 循环不一样的地方是，模型说“我做完了”不算数，程序要按真实状态核对一遍。

1.1 启动阶段（进入循环前）

抢占 lane

runLane(botId, sessionId) 加锁，同一 lane 同时只能有一个 run。这一步之前没有任何 await，两次并发启动不会同时通过检查。

创建 RunRecord

记录 status=running、workspaceDir、来源（peerOrigin / groupOrigin）、supersedesRunId、resumedFromRunId，然后立即落盘。

预算定时器

maxMinutes 到期后 abort，错误信息是“达到本次执行时间预算”，执行记录保留。

选择历史槽

根据来源确定 contextKey：主会话、工作会话、Peer 私有会话或群工作区（见第 4 节）。

组装系统层

身份/SOUL + harnessInstructions()，提示词只提到本轮真正提供的能力（computer、host、design、peers…）。

WorkItems.begin

识别 /plan、/goal 命令，或者接上之前的计划/目标；状态为 planning 时只开放只读工具。

1.2 单轮迭代

① 收集输入消费用户对 request_user_input 的回答；群聊调用 groups.receive 拉取新收件
→
② 预算检查RunPolicy.check：maxTurns / maxMinutes / maxTokens，超出时抛出 AppError
→
③ checkpoint有新私聊输入或群事件时抛出 InputUpdated / GroupUpdated，主动让出
→
④ 选工具turnTools 按能力、场景、计划状态过滤，MCP 工具每个 run 只取一次
→
⑤ 准备上下文ContextEngine.prepare，必要时压缩
→
⑥ 推理model.complete 流式输出，推理过程单独展示
→
⑦ 分支没有工具调用：进入完成门禁；有工具调用：执行工具批次

1.3 推理失败的就地恢复

异常处理
ContentPolicyErrorquarantinePolicyContext 隔离触发审核的历史片段，用 force 重新 prepare 上下文后重试一次
ContextOverflowError服务商报上下文溢出时强制压缩后重试；压缩后请求和原来一模一样就直接抛出，避免死循环
模型 5xx / 空闲超时ModelClient 内部按 modelRetries 退避重试，配置了 fallbackModel 时切换一次备用模型
新输入打断runtime.inference.abort(new InputUpdated()) 只中断这次推理，已执行的工具结果都保留

1.4 完成门禁（模型没有调用工具时）

模型想直接回答时，Harness 按下面的顺序逐项检查。任何一项不满足，就往历史里插一条 system 续写指令（prompts/continuations.ts），然后 continue 回到循环：

#检查项未通过时
1有待用户回答的问题waitQuestions 挂起等待，不消耗模型调用
2任务终端还在运行runningTerminals，要求读取或结束终端
3接受了委托但没交回执missingDelegationReceipt
4Python 会话 / 后台进程未结束unfinishedPython / unfinishedProcesses
5计划里还有 pending / working 步骤PLAN_INCOMPLETE，连续 3 次提前回答就停止（群聊里标记为受阻）
6planning 状态下还没保存计划，或 goal 还在进行PLAN_NOT_SAVED / GOAL_INCOMPLETE
7受托写入的记忆还没真正保存MEMORY_NOT_SAVED，最多提醒 2 次，之后报错
8执行账本里有未解决的失败unresolvedFailures，最多 2 次，之后报“执行仍有未解决错误”
9群聊：发布前复核、被点名必须回复groups.beforeFinal / mentionCheckFailed
10表情事件要求回复却选择了静默REACTION_NEEDS_REPLY
计划步骤要标记为 done，必须引用本任务里真实成功的 executionId 作为证据（RunPolicy.update 会校验），所以模型没法凭空宣称“已完成”。

1.5 工具批次与防死循环

意图先落盘

每个调用在执行前先 ledger.begin()，并写入 journal('tool.intent')，然后才真正执行。

并发执行

runConcurrentTools：读类工具并行，独占类工具串行，写同一路径时加路径锁。

拒绝即停止

用户拒绝授权（InteractionDenied）后，本批剩下的调用都标为“未执行”；stopTask 会结束整个 run。

同一失败 3 次

按 execution.targetKey 统计，同一目标连续失败 3 次就暂停，避免无效重试。

群聊停滞检测

工具结果去掉时间戳、ID 后做指纹，连续 3 批没有新的成功结果，就把任务标记为受阻。

finishRun 收尾

停止残留的进程、终端、Python 会话，修复工具配对（repairHistory），收集产物，触发后台学习。

02上下文策略：组装、预算、裁剪、压缩

electron/core/context/context-engine.ts · context-budget.ts · context-view.ts · context-pruning.ts

原始历史（conversations[contextKey]）只追加、不修改，始终是权威记录。发给模型的是在它基础上算出来的“视图”：由 epoch（压缩代次）、through（前面多少条已并入摘要）、pruning（工具输出裁剪）和 view（插入点记录）共同决定。这些状态都存在 SQLite 里（context_heads / context_state / context_pruning）。

2.1 请求的分层结构（按稳定程度排列，为了命中 prompt cache）

system身份 + SOUL + Harness 指令（一个 run 内不变）
tools工具 schema，顺序固定（TOOLS 只能追加，不能调换顺序）；MCP 工具每个 run 取一次
prefixContext记忆快照 · 本机环境/工作区约定 · 技能目录 · MCP 服务列表 · 设计任务前缀
summary“历史压缩摘要 + 精确记录锚点”（resultId / path / sha256 / commit）
loadedSkills / restoredFiles本会话读过的技能；压缩时重新读取的最近文件（最多 5 个）
history view从 through 开始的历史，经过工具输出裁剪和图像归档
controlstaskFrame（计划/目标/设计状态）+ dynamicContext（turnContext：请求锚点、时钟、@ 信息、群事件）
只追加的 ContextView：参考资料或控制信息变化时，不会回头改前缀，而是在当前历史位置插入一条“参考资料已更新…”事件。这样之前已经付费缓存的前缀依然有效。插到对话中间的 assistant 参考消息会改成 system 角色，因为 DeepSeek 这类 thinking 模型会要求 assistant 消息带 reasoning。

2.2 预算公式 contextBudget(capacity, compactPercent=85)

output   = capacity ≥ 160k ? 8192 : clamp(capacity*0.2, 1024, 4096)    // 输出预留
safety   = clamp(capacity*0.08, 768, 8192)                               // 安全余量
input    = capacity - output - safety                                    // 输入上限
trigger  = min(input - headroom, capacity * compactPercent%)             // 触发压缩的阈值
tail     = max(1200, min(input*0.3, max(24000, input*0.12)))             // 原样保留的尾部
summary  = max(min(3000, max(600, input*0.12)), min(8000, input*0.03))   // 摘要目标长度
compaction = max(output, min(32000, summary*2+2048, capacity*0.25))      // 压缩调用的输出额度

Token 计数用 o200k_base，在 worker 线程里预先计数并缓存（primeTokenCounts），再用服务商返回的真实 usage 校准系数：偏低时马上调高，偏高时要多次观测后才慢慢调低，并且不会低于未校准的值。图像按 768px 分块、每块 1024 token 预留。

2.3 prepare() 的降级流水线

1 图像归档截图超过 32 张（设计任务 8 张）后，只保留最近几张
→
2 工具输出裁剪超过 trigger 时，把保护尾部之外大于 350 token 的输出换成摘要（resultDigest）
→
3 激进裁剪仍超过 input 时，连最新的已归档结果也只留引用
→
4 必要项检查system + 参考 + 控制本身就超窗时，抛出 ContextCapacityError
→
5 压缩循环最多 8 轮，把 tail 之前的记录并入摘要

2.4 压缩（Compaction）细节

切分点

  • tailBoundary 以“交换”（assistant+tool_calls+tool 结果）为单位，至少保留 2 个完整交换
  • 切分点不能落在没配对完的工具调用中间
  • 摘要输入放不下时按交换对半缩小范围

复用缓存

  • 优先在刚组好的请求后面追加一条“压缩请求”，system、tools、前缀都相同，大部分输入能命中缓存
  • 模型在这个请求里还想调工具时，退回到不带工具的序列化请求

结构化摘要

{"goal","userMessages","constraints","files",
 "done","pending","decisions","failures","next"}

done 只写有工具结果证实的操作，计划和实证分开写；JSON 不合法时调用一次修复，然后在本地截短到合适长度。

提交 epoch

  • 提交前用 hash 校验被压缩的那段原始历史没有变化
  • 压缩后没省下至少 100 token 就回滚
  • 恢复的文件不会再引发新一轮压缩

失败降级

  • 摘要模型失败后冷却 60 秒
  • 仍然超窗时用 localSummary 按规则机械摘要，任务继续跑

手动压缩

  • compactContext(focus)：Bot 空闲时立刻执行，忙时排到下一次请求前
  • focus 指定要优先保留的细节

2.5 工具结果的“外置 + 回查”

每个工具结果的完整内容都写到 results/<resultId>.json，上下文里只放一个信封：{executionId, resultId, truncated, readWith:'read_result', result}。内联预算是 toolResultLimit = clamp(context*0.1, 6000, 24000) 字符。超出时保留 JSON 结构和所有标量字段（exitCode、sha256、eof…），只从中间截短长字符串；stdout/stderr/log 这类字段多保留尾部（头尾 4:6），因为报错通常在最后。之后模型可以用 read_result 分页读取原文。

被压缩掉的内容不会丢：原文还在，模型可以用 history_search / history_read / read_result 按锚点找回，这也是摘要里要带“精确记录锚点”的原因。

03工具模块设计

agent/tools/definitions · agent/tools/handlers · tools/*.ts

3.1 定义与实现分离

definitions/

只放 JSON Schema 和描述，原样发给模型。TOOLS 数组顺序是请求的一部分，影响 prompt cache，新工具只能往后加。

handlers/

TOOL_HANDLERS 按名字精确匹配；PREFIX_HANDLERS 按命名空间匹配（scheduled_ / group_ / mcp / design_）；mcp__* 是 MCP 原生工具。

ToolDeps 注入

handler 拿到的是 ToolContext（bot、args、signal、run、workspace、deps），不直接依赖 Harness，方便测试。

3.2 每轮动态选工具：turnTools()

维度规则举例
能力开关没有 VM/Host 时去掉文件和命令工具；没开桌面控制时去掉 host_computer；没有 scheduler 时去掉 scheduled_*
场景群聊里禁止 memory / skill_save / 委托；Peer 私有会话只有 privateTools；headless 模式隐藏需要人工交互的工具
计划状态planning 时只给 PLANNING_TOOLS（只读），tools_batch 的 enum 也收窄成只读工具
小窗口模型上下文小于 32k 时只发 COMPACT_TOOLS，其余工具通过 tool_search 找到，再用 code_exec 里的 tools.xxx() 调用
MCP 预算最多 min(60, 120-内置数) 个函数，schema 占用不超过输入预算的 10%（上限 12k token），其余服务只列在提示里，通过 mcp_call 调用

availableTools（实际能调用的）和 modelTools（展示给模型的）是两个集合。执行前会再校验一次：工具是否注册、本轮是否可用、参数是否符合 schema（validateToolArguments）。

3.3 并发模型

EXCLUSIVE_TOOLS（串行）: computer, exec_command, host_file_write, apply_patch, memory,
                        bot_send_message, group_send_message, design_*, ...
PATH_LOCKED_TOOLS     : file_write, file_patch   → 按 "vm:/path" / "host:/path" 排序加锁，防止死锁
其它（读类）           : 并发执行，上限 parallelReads（1–8）

批次里遇到串行工具时，要等前面已经在跑的调用都结束；用户中途停止时，通过 AbortSignal 级联取消整个批次。

3.4 组合与长生命周期工具

tools_batch

只读流水线，后一步可以引用前一步的结果（tool-pipeline.ts）。

code_exec

在沙箱代码里编排多个工具调用，每次嵌套调用都走 invokeNested，同样记账和校验。

终端 / 进程 / Python

TerminalSessions、BackgroundProcesses、PythonSessions 按 run 归属，run 结束或取消时统一回收。

文件检查点

写文件前保存 beforeHash 和备份，可以用 checkpoint_restore 回滚。

权限：Host 侧操作经过 Interactions（审批弹窗、权限模式）。被拒绝时，工具结果里带 operationDenial 和 DENIAL_GUIDANCE，告诉模型不要换个方式绕过。所有路径和输出都经过 host.redact 脱敏。

04会话管理

agent/run-lanes.ts · storage/store.ts · storage/state-database.ts

4.1 Lane：并发的基本单位

一个 Bot 在每个 lane 上同一时间只做一件事，不同 lane 之间可以同时跑。主 lane 就是 botId（私聊，加上它的群工作和受托任务），每个工作会话单独一条 lane，标识是 botId#sessionId。laneMatches(lane, botId, sessionId) 的 sessionId 参数有三种语义：undefined 表示所有 lane，null 表示主 lane，字符串表示指定的工作会话。

4.2 历史槽（contextKey）

场景contextKey说明
主私聊botId带记忆（Cognition），参与后台学习
工作会话Store.sessionHistoryKey(sessionId)有独立的历史、上下文、工作目录和计划
Bot 间私聊peer:<privateSessionId>和主会话隔离，需要真正干活时调用 start_main_task 转进主会话
群工作区group:<gid>:<botId>:v2[:reset:t]Bot × 群单独压缩；重置上下文时换一个新 key

4.3 输入抢占与合并

refreshInput

Bot 工作时用户发来新消息：标记 runtime.updated，只中断当前推理；正在等审批的操作也一并取消，避免旧授权被用在过时的操作上。

排队合并

排队中的多条输入通过 inputMessageIds 一次性交给下一个 run，并加上 BATCHED_INPUT_CONTEXT 说明。

supersedesRunId

新 run 接替被打断的 run，继承它的计划和上下文；但只在同一会话来源内继承，私聊不会继承群里的 run。

4.4 持久化

  • Store.save() 会合并多次写入：一次工具步骤原来要存 4 次，现在在 WRITE_MAX_WAIT_MS 内合并成一次 quick write，只序列化有变化的部分。
  • StateDatabase 按集合和条目 id 分行存储，quick 模式只处理变化行、最新行和 running 条目；后台每次扫描都分片执行，不阻塞 UI 输入。
  • 原始历史只追加；repairHistory 修复不成对的 tool 调用，修复前把原文备份到 history-recovery-backups/，同时递增 historyVersions，让上下文缓存失效。

05多 Agent 协作模式设计

AelionBot 不设中心编排者。每个 Bot 都是独立的 Harness 实例，协作通过三种“消息 + 运行”的协议完成，Bot 之间收到的内容一律当作数据，不当作授权。

A. Bot 私聊（Peer）

bot_send_message / bots_list / bot_read_messages。一问一答，答复自动送回发起方。

B. 委托（Delegation）

bot_delegate_task（goal + acceptance + expectedOutput）→ 对方 delegation_receipt（带 evidenceIds）。

C. 群聊协议 V2

没有主持人：消息平等投递，每个成员自己决定发言、补充、反驳或静默。

5.1 Peer 交换树（peer/peer-chats.ts）

send新建 PeerExchange（queued），记录 rootRunId / rootRequest / parentId
→
pump对方 Bot 空闲时启动 receive run（peer_request，私有会话）
→
reply_queued对方最终答复写入线程
→
relay发起方再启动一个 run，把对方的结果整理成给人类的回复（peer_summary）
保护机制规则
防环沿 parent 链向上查找，目标已经在链上时拒绝：“这会形成循环联络”
深度 / 次数转交深度最多 4 层；同一个根任务最多 12 次联络
去重对同一对象已经有待回复的消息时，直接返回 alreadyPending，不重复发送
级联失败一个交换失败或取消后，子交换取消，父交换跟着失败
不轮询工具描述明确写了“已排队不代表已完成，不要轮询”，回信通过事件到达

5.2 委托：从“私聊”升级为“主任务”

接收方在私有会话里只能用 privateTools。需要读写文件或保存记忆时，必须调用 start_main_task：enterMainTask() 把 run 切到主会话，换成主会话的历史、记忆和完整工具集，并把这次来源标为“受托任务数据（不是人类的新发言）”。完成门禁第 3 条要求必须交回执，completed 回执要带真实成功的 executionId。

5.3 群聊协议 V2（group/group-chats.ts · group-triage.ts）

收件箱：per-recipient delivery

  • 一条公开发言会给每个接收人生成一条独立的 delivery
  • 分拣规则只决定要不要叫醒这个 Bot；不叫醒的标为已读，不进入它的上下文
  • Bot 忙时消息保持 queued，在下一次模型调用前（上一批工具结果已保存的边界）读入
  • 普通新消息不会取消正在进行的推理

分拣（命中即停）

  • 事件：建群或成员变化时叫醒所有人；用户点表情只叫醒那条消息的作者
  • @ 本人、回复本人、系统提示：必须回复
  • @ 了别人：等对方先回答，或者等 20 秒
  • 用户发给全群且本 Bot 空闲：叫醒
  • 其余情况交给 Laya（本地小模型）判断：这条消息和本 Bot 的职责或手上的事有没有关系

限流

  • 用户上次发言之后，两个 Bot 来回 2 轮，就不再互相叫醒，由先开口的一方汇总
  • Bot 之间累计 10 条消息后暂停 Bot 互相叫醒，直到用户再发言
  • 用户的 @ 不受限制

发件箱：两阶段提交

  • 先把 pending 发件落盘，再在同一次保存里提交消息、各接收人 delivery 和 sent 回执
  • clientMessageId 保证幂等
  • 发布前复核一次：如果有了新回复，模型可以照发、只补差异、改成表情或不发
  • group_pass 表示不发言直接结束
群聊的系统层按变化频率拆成多条消息：groupContext（很少变）→ groupSharedContext → persona → 每次唤醒的 turnContext。被反复唤醒时，只有最后那一小块会变，前缀缓存能一直命中。

06可观测性

事件日志 events.jsonl

Store.journal(type, payload) 只追加：tool.intent、tool.result、execution.started/finished/resolved、run.verification、model.usage、interaction.decision、permissions.mode、connector.*、python.cancel.unknown…。参数先脱敏（redact）再写入。

执行账本 ExecutionLedger

每次工具调用记录 status（running / succeeded / failed / cancelled / unknown）、target/targetKey（同一操作的稳定标识）、paths、resultId、error。之后对同一目标的成功执行会自动把之前的失败标记为 resolved。界面上可以按 run 查看。

模型用量与时序

modelUsage 按 run 记录输入、输出、缓存命中 token；RequestTiming 记录 firstTokenMs、firstToolMs、lastEventMs、responseBytes、toolArgumentChars；run.modelRequest.phase 实时推送给界面（等待中 / 流式输出）。

上下文概览

contextOverview 按 system / conversation / mcp / skills 统计 token 占用；ContextStats 包括 epoch、compactions、prunedOutputs、archivedImages、contextChanges（system-change / compaction / reference-update…）和 lastIssue。

Prompt Cache 诊断

PromptCacheDiagnostics 只保存哈希和大小，不存正文。它对比相邻两次请求，给出 firstDifference（tools / system / message / request-options…）、第一处不同的消息序号、增减的工具，用来定位缓存失效的原因。

诊断包 Diagnostics

错误写入 diagnostic-events.jsonl，超过 256KB 自动轮转。导出诊断时汇总最近 50 个 run、每个 run 最近 20 次执行、事件尾部和 VM 日志，密钥和路径全部脱敏，Bot 用编号代替。

压缩尝试与 Laya 决策日志

contextAttempt 记录每次摘要的原文和校验错误；LayaDecisionLog 记录群分拣的判断，方便回看某个 Bot 为什么被叫醒或没被叫醒。

实时工作视图

liveWork() 列出正在运行的终端和进程，可以单独停止；ReplyStreams 推送流式回复和推理过程的尾部。

07长任务断点续跑设计

核心原则：不自动重放外部操作。崩溃以后，执行结果未知的操作会明确标为 unknown，让模型（和用户）先核对实际状态再继续，而不是盲目重试一次可能已经执行过的写操作。

7.1 启动时的状态修复（Store 构造）

对象修复动作
running 的 RunRecord改为 interrupted，错误信息：“应用中断。请检查已执行的操作后继续，系统不会自动重复工具调用”
running 的 execution改为 unknown：“操作结果未知，继续前先核对实际状态”
running / planning 的 WorkItem改为 paused，清除 activeRunId
queued 的输入消息改为 interrupted
所有历史repairHistory 补齐或删掉不成对的 tool 调用（先备份），递增 historyVersion
群 delivery / Peer exchange标为 interrupted，可恢复（resumable）的等用户点“继续本轮讨论”
定时任务已经认领的 occurrence 不重放，记录不完整的标为 interrupted

7.2 续跑流程

resumableRun状态必须是 failed / cancelled / interrupted，并且是最新的任务
→
容量检查之前是因为上下文不够失败的，要求先调整模型设置再续跑
→
重建输入原始人类消息、WorkItem.objective 或附件
→
run(resumeRunId)继承 workItemId、workspaceDir、附件，追加 RESUME_CONTEXT

计划延续

WorkItem 记录所有 runIds 和 plan。新 run 用 WorkItems.begin 接上，把 plan 拷到 run 上，模型能看到哪些步骤已经完成、证据是什么。

账本跨 run 合并

ledger.forTask() 沿 resumedFromRunId 链和 WorkItem.runIds 汇总执行记录，之前未解决的失败和 unknown 会进入 pendingFailures，必须用 execution_resolve 说明处理结果后才能完成。

上下文不重算

压缩 epoch、裁剪状态和 view 都存在 SQLite 里，续跑时直接接着用，不需要重新摘要；history 版本变了才重置。

预算中断可继续

maxTurns / maxMinutes / maxTokens 耗尽时抛出带 code 的 AppError（budget.*），run 标为 failed，记录保留，可以直接继续。

协作任务的恢复

群聊和 Peer 任务要从原会话恢复：群 delivery 重新排队带上原 run，Peer 用 retryRun 重新进入 queued 或 reply_queued，父交换回到 waiting。

停止也保留现场

用户停止时，finishRun 会停掉进程、终端、Python，未完成的操作标为 cancelled 或 unknown；文件检查点保留，可以回滚。

08设计原则小结

证据优先于口头声明

计划步骤、委托回执、记忆写入都要引用真实成功的 executionId；摘要里的 done 也只写有工具结果证实的内容。

缓存友好

工具顺序固定，上下文按稳定程度分层，变化只追加不回改；压缩时复用已缓存的前缀，再用诊断工具定位缓存失效点。

原文不丢

历史只追加，结果外置，摘要带锚点，修复前先备份；任何裁剪都能通过 read_result / history_read 找回原文。

有界自治

轮数、时间、token 预算；同一失败 3 次、提前回答 3 次、停滞 3 批就停；Peer 链深度和次数有上限，群聊有限流。

数据和授权分离

Bot 消息、工具截图、附件都标明“不是新的用户指令”；只有应用核验过的委托才能写入目标 Bot 的记忆。

可中断、不重放

中断后标为 unknown 交给人核对；输入抢占只中断推理，不丢弃已经执行的工具结果。
